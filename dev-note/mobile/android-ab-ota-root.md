# Android A/B OTA 后保留 Root：匹配构建、阶段与启动镜像

> A/B OTA 会更新目标槽的启动链；保留 Root 的关键是遵守当前工具和机型的更新流程，不能把历史 boot 当作通用恢复镜像。

## TL;DR

- 先确认实际设备、ROM 完整构建、活动槽与 Magisk 版本，区分日常 OTA 和跨版本升级。
- “安装到非活动槽”只适用于成功安装 OTA、尚未重启等前提，不是随时可执行的准备动作。
- 更新后同时验证 ROM、槽、Magisk 与 `su`，App 图标保留不代表 Root 保留。

## 更新前要能回答的问题

| 项目 | 为什么需要 |
| --- | --- |
| 设备型号、代号、完整构建 | 相近机型或不同构建的镜像不可混用 |
| A/B 布局、当前槽和更新方式 | 决定 OTA 目标、恢复流程和工具适用性 |
| Root 使用的启动分区 | 不同设备可能涉及 boot、init_boot 或其他布局，不能写死 |
| 当前构建的原版镜像与校验值 | 作为恢复和对照来源；哈希只证明相应文件一致 |
| 用户数据备份与恢复入口 | 只有 boot 备份不等于完整系统或数据可恢复 |
| 只读分区是否被手动修改 | 更新器可能校验失败，先依据实际错误判断 |

可读取设备状态，多设备时显式指定目标：

```sh
adb shell getprop ro.lineage.version
adb shell getprop ro.boot.slot_suffix
adb shell su -c 'magisk -v; magisk -V; id'
```

这些命令要求相应 ROM／Root 可用。槽名应每次重新读取，不固化成 A 或 B。

## 通用阶段模型

```text
匹配版本与备份
  → 按对应指南恢复原始镜像（若要求），保持当前系统运行
  → 官方 OTA 安装与优化完成，尚未重启
  → 按 Magisk 流程修补已更新的目标槽
  → 从指南指定入口重启
  → 核对新构建、活动槽和 Root
```

这张图用于理解阶段，执行前仍须阅读当前 Magisk 版本和具体机型的官方指南。Magisk 的通用 OTA 流程有机型限制，不能据此保证每个 ROM 或更新器都适用；有的机型不要求预先恢复镜像。

不把“关闭自动系统更新”当作 OTA 必定安全的证明；它只减少非预期更新／重启。恢复镜像失败、OTA 未完成或修补报错时，保留日志并停止后续写入，先重新核对状态。

跨 ROM 大版本、recovery sideload 和内置 Updater 的步骤可能不同；GApps 等附加组件也要遵守该机型升级说明，不能把同分支 OTA 清单直接套用。

## 失败后的判断

系统能启动但 Root 丢失：先读取更新后实际构建，再取得相同来源、相同构建的正确启动镜像，在目标设备按 Magisk 说明修补。不能把旧版本已打补丁 boot 刷到新 ROM。

无法启动或 OTA 未完成：先识别故障阶段、槽与可用恢复模式。A/B 两槽可能版本不同，用户数据又是共享的，不能承诺切回旧槽就能无损恢复。

2026-10-20 案例完成了镜像备份和哈希核对，未执行实际 OTA。因此能沉淀匹配与验收方法，不能把那次备份写成“保留 Root 流程已实机跑通”。
