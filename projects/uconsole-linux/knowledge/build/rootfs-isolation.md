# rootfs 构建隔离与文件元数据

> rootfs 是一个受管理的目标文件树；chroot 不隔离挂载，也不会自动保护宿主设备或文件元数据。

## TL;DR

- 在私有挂载命名空间组装 rootfs，按需创建伪文件系统；卸载完成前不要删除工作树。
- 编译依赖属于构建宿主或构建容器；运行包属于 rootfs。不要为了安装应用把整套编译环境带入镜像。
- 复制文件树时保留 UID/GID、模式、硬链接、xattr 与 capability；项目配置则显式指定安装权限。
- 构建 spec、账户哈希和网络配置按敏感材料处理，不把它们加入公开产物和日志。

## 本仓库已有机制

Ubuntu Base 后端（工程源码：`scripts/image_backends/ubuntu_base.py`）的 `build()` 使用
`unshare --mount --propagation private`，`chroot_mounts()` 为目标挂载 `dev`、
`proc`、`sys` 和独立 `devpts`，并按逆序卸载。它没有把宿主 `/dev` 整体绑定给目标。
该隔离服务于可信构建流程，不是执行未知代码的安全沙箱。

`prepare()` 创建权限为 `0700` 的工作目录和 `0600` 的 spec；明文账户密码先变为
哈希再写入 spec。哈希仍能被离线猜测，不能因此公开 spec。配置输入和日志也可能含无线网络凭据。

镜像导出器（工程源码：`scripts/image_backends/rpi_image.py`）的 `_validate_paths()`
拒绝物理设备路径、宿主 `/`、位于 rootfs 内部的输出及仍有子挂载的 rootfs。
`_root_payload()` 跨文件系统复制使用 `rsync -aHAX --numeric-ids`，保留文件树的重要元数据。相同文件系统的临时调整在 `finally` 中恢复。

## 可迁移的实现原则

构建依赖预检应在昂贵工作前一次报告缺失项。应用可以先在宿主交叉编译，或在受控构建环境生成带摘要的安装包，rootfs 阶段只安装已验证产物；不能让“安装”悄悄触发源代码下载与现场编译。

资源清理记录本次成功挂载的项目，按相反顺序释放。卸载失败时保留错误与工作目录，避免清理命令穿过仍有效的挂载点。不要以删除全部工作目录来掩盖失败。

已有系统文件树使用能保留元数据的复制方式；项目自有配置采用明确的安装路径、属主和模式，避免把仓库检出的组写权限原样带入 `/etc` 或 systemd 单元。不要对整个 rootfs 递归改权限，发行版的特殊文件和 capability 可能有明确用途。

usrmerge 的 `/lib -> usr/lib` 等链接是布局契约。候选内核解包与恢复方法已有[专门条目](usrmerge-kernel-staging.md)，不要通过通用 tar 解包覆盖链接。

## 证据与未知

以上“已有机制”来自当前源码；隔离、复制与权限策略不证明特定镜像已通过设备启动。元数据保留可用包含符号链接、硬链接和 xattr 的临时夹具验证，不能只比较文件内容摘要。真实文件 capability 的验证还取决于运行用户权限和文件系统支持，应单独记录环境限制。
