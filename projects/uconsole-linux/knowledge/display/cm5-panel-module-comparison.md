# CM5：CWU50 模块的受控对照

> CM5 同内核替换面板模块并显示已知色条，才支持驱动功能正常的结论。

## TL;DR

- 固定内核、DT、供电和背光，用精确 headers/config/符号版本构建单模块。
- 停止占用 DRM 的桌面，替换驱动并写已知 framebuffer 色条，检查实体画面。
- 用户确认候选色条可见；稳压器引用和热替换条件限制该结果，不能外推独立冷启动。

## 方法：按 ABI 和主机生命周期做单模块对照

1. 固定正在运行的内核、DT、供电与背光，保存 boot ID 和原模块；用精确 headers/config/Module.symvers 构建候选。
2. 停止占用 DRM 的进程，先解绑 RP1 DSI 平台主机，再卸载面板；加载候选后重新绑定主机。
3. 在重新创建的 framebuffer 写入已知色条，检查字节读回与实体画面，并分别记录结果。
4. 恢复时按同一顺序换回原模块；保留冷启动电源状态与热替换引用的限制。

该主机持有面板及 DRM 引用，仅卸载面板不足以完成隔离。具体 ABI 和热替换异常见下文证据；
本方法只归纳已执行的 CM5/RP1 对照，其他显示主机须先核对自己的绑定与清理路径。

## 基线与固定条件

用户确认这块 CM5 使用原有镜像时能够正常显示。运行中的基线为 CM5 Rev 1.0、
内核 `6.12.94-v8-16k+`，镜像自带的 `panel_cwu50` 选择了旧屏分支。
这不能独立确认实体面板的 IC 型号，也不能证明该软件包对应的源码提交。

对照过程中保留了运行中的内核、CM5 硬件、运行时设备树、RP1 DSI 驱动、
OCP8178 背光驱动及供电配置。启动 ID 始终为
`00000000-0000-4000-8000-000000000021`；运行时 DTB 在替换前后的 SHA-256 均为
`93272484c1c3d4d9fde7cf5554f827969c8e3e9e12cc1c5cca926d4ebfe75ed7`。
未替换启动配置、软件包中的模块、EEPROM 或磁盘镜像。

两个帧缓冲测试阶段前均已停止 LightDM。替换前，DRM 客户端及文件占用检查结果均为空。
两个阶段都将同一幅 720x1280 XRGB8888 图像直接写入 RP1 帧缓冲：白、黄、青、绿、
品红、红、蓝、黑色带。每次写入均覆盖 3,686,400 字节，读回内容与写入内容完全一致，
图像 SHA-256 为
`daf3314cac1427e2ef1fa92cef8d7701fcf2075f9c6c946e05e1510cdaca4174`。
基线阶段的彩条本身未得到目视确认。背光设置保持为亮度 `5/9`、`bl_power=0`。

## 候选模块身份与构建证据

候选源码与 `kernel/patches/0001-drm-panel-add-clockworkpi-cwu50.patch`
中的完整驱动逐字节一致；源码 SHA-256 为
`3265d0af5ddf1399ae435ebbcdbdfe44644484793207802c61dcd1beb3fd8b1a`。
仅在本机编译了面板模块及必要的主机构建工具，使用的是与设备完全对应的头文件、
配置和 `Module.symvers`。重建主机工具前，对复制的 6,871 个普通头文件逐一核对了
校验和。没有使用容器、下载新工具链或构建完整内核。

主机现有交叉编译器为 GCC 16.2.1；运行中的内核记录的编译器为 GCC 14.2.0。

`6.12.94-v8-16k+ SMP preempt mod_unload modversions aarch64`。
候选模块包括 `module_layout` 在内的全部 36 项版本条目均与对应符号表匹配；
全部 35 个未定义全局符号的 CRC 均匹配。目标系统启用了 `CONFIG_MODVERSIONS=y`，
未强制校验模块签名。候选模块在未使用强制加载选项的情况下成功加载。

## 替换观察与恢复

屏幕属于平台主机 `drm-rp1-dsi/1f00130000.dsi`，不是独立的 VC4 HDMI 设备。
仅移除面板模块会留下主机及 DRM 对面板的引用。因此，在停止占用显示设备的桌面进程后，
先解绑 RP1 平台主机。其 MIPI 子设备和帧缓冲随之消失，随后正常卸载原面板模块。
再从 `/tmp/uconsole-panel-ab/candidate-panel-cwu50.ko` 加载候选模块，重新绑定
RP1 主机。新的 MIPI 子设备绑定到候选模块，并重新创建 `fb0`。

在加载候选模块前，移除原驱动时产生了一条 `mipi_dsi_detach` 警告和两条
`_regulator_put` 警告。重新绑定主机时，RP1 记录了
`Failed to acquire type ID 2 for interface type DSI, ret -28`，并将连接器注册为
`card3-DSI-3`，而非 `card0-DSI-2`。它报告已连接并启用，模式为 720x1280。
原驱动的 prepare 启用两路电源，但 unprepare 中没有对应的关闭操作；移除后仍保留
先前的电源启用引用。因此，这次热替换对照不能验证候选驱动独立冷启动时的电源管理。
卸载及重新注册过程中观察到的现象也限制了对照的纯净程度；没有进一步证据时，
不能把它们归因于候选模块初始化。整个过程中 SSH 始终可以响应。

软件包中的原模块未变，并额外保存了一份临时备份。恢复操作采用相同顺序：解绑主机、
卸载面板模块、加载原模块、重新绑定主机，然后写入同一图像，不启动桌面。
已将以 root 运行的恢复脚本放在 `/tmp/uconsole-panel-ab/restore-original.sh`，
并检查了 shell 语法；由于对照成功，没有执行恢复。用户确认画面后进行的只读检查
发现候选模块的 srcversion 为 `595E0C010EFD28B29392C37`，内核及启动 ID 相同，
背光设置未变，LightDM 已停止，屏幕显示彩条。随后正常关闭 CM5，供用户换回 CM4。
替换模块仅从临时文件加载；软件包中的原模块保持完整。

本次热替换模块测试满足了目视验收标准。后续调查 CM4 的 DSI 主机、设备树配置、
时钟、复位及供电时序时，应保留这份精确源码作为已工作的对照。该结果没有确定
CM4 的故障原因，也未验证所有面板分支，更不能证明使用工程内核可以冷启动显示。

替换前后的原始状态、内核日志、帧缓冲写入程序、模块备份和 ABI 报告保留在 Git
之外的 `~/.cache/uconsole-cm5-panel/`。记录的结果是：CM5 热替换后显示通过目视
确认，但受上述验证范围限制。
