# 模型应用响应慢：分开测请求、重试与显示队列

> 用户看到的等待可能横跨多个请求和显示阶段；先建立端到端时间线，再决定调整网络、模型、网关或 UI。

## TL;DR

- 连接测试、首个流式事件、完整生成和屏幕显示是不同终点。
- 单次尝试的超时，不保证应用总等待同样短。
- 后台已完成而前台未显示，需要检查展示队列和交互状态。

## 最小时间线

| 时刻 | 观察点 |
| --- | --- |
| T0 | 用户提交或应用触发任务 |
| T1 | 实际发出上游请求 |
| T2 | 收到 HTTP 响应头 |
| T3 | 收到首个有效事件或内容 |
| T4 | 请求完成或失败 |
| T5 | 内容实际展示给用户 |

按请求 ID 关联客户端、桥接和上游日志。连接时间、首响应时间和生成时间的定义必须一致；仅看 UI 的“正在输入”不能区分这些阶段。

首个流式事件可能只是角色或状态元数据，不等于首个内容 token；需要分别记录时应明确命名两个指标。

串行流程的等待可由多次尝试、退避、后续补充请求和显示排队累积。并行阶段不能简单相加；需要从实际调度时间线计算关键路径。

## 分情况处理

- **T1 很晚**：检查客户端任务队列、限流或前置工作。
- **T2 很晚或收头前重置**：检查路由、连接复用、网关和上游可用性；按[路径诊断](../dev-note/network/proxy-path-diagnostics.md)做对照。
- **T3 很晚**：检查是否真的启用流式、缓冲层，以及模型或应用的生成过程；HTTP 成功不代表及时产生内容。
- **T4 很晚**：核对输出规模、工具耗时、取消与重试；不要仅延长所有超时。
- **T4 已完成、T5 仍未到**：检查气泡/消息队列、动画、悬停暂停和应用可见性。

某些应用先发主回复，再独立请求补充内容；这是两次模型调用。某些气泡还要等前一个消失才展示。它们是需要从当前应用确认的机制，不是所有模型客户端的统一行为。

## 超时与复测

给连接、读空闲、单次请求和整个用户操作分别定义预算。若保留重试，同时限制尝试次数和总预算，核对错误是否会在多层重复重试；具体语义取决于 HTTP 库与客户端实现。

调整后使用相同任务重复测量，报告时间分布和失败率，而非一次最快结果。网络稳定、流格式正确也不等于回答质量已改善，需另行检查模型选择、上下文和工具结果。
