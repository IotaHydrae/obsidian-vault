# 桌面应用接入 MCP：分层验证，而非只看服务启动

> 原生应用扩展、桥接进程和 MCP 客户端是不同层；最终应以读取正确的当前工程验证整条链路。

## TL;DR

- 分别验证应用、应用侧扩展、MCP 握手、工具发现和一次安全读取。
- 在项目中启用服务是配置作用域选择，不自动构成操作系统权限或应用工程隔离。
- 安装包校验、工程导出校验和语义回读分别证明不同事情。

## 接入检查

| 层次 | 验证内容 |
| --- | --- |
| 原生应用 | 版本、账号状态、目标工程或文档是否实际打开 |
| 应用扩展 / 桥接 | 版本兼容、实际连接端点和实例是否匹配 |
| MCP 初始化 | 协议握手与能力协商成功 |
| 工具发现 | 所需工具确实出现在工具列表，而非仅进程存活 |
| 端到端 | 安全读取当前工程，核对工程标识及内容 |

已有进程、端口可达或工具列表存在，都不足以证明连接到了预期应用实例。一个桌面应用可能跨工程共享会话，发起操作前仍须核对当前对象。

## 作用域与操作边界

按客户端支持的方式为需要的项目配置服务，重开会话后确认实际加载状态。凭据、服务能力和访问范围仍由各层分别控制；不要把“仅某项目启用”当作对服务可访问文件的强制限制。

先做只读验证，再处理明确要求的修改。涉及原生工程编辑时，在可恢复副本上验证，并记录工具返回值与应用内实际结果。

## 备份究竟验证了什么

- 文件或压缩包存在，不等于备份完整。
- 校验和与压缩包测试可确认对应字节及容器完整性，不能证明重新导入后的语义一致。
- 需要恢复保证时，在独立副本中回读并核对关键对象、连线或属性。
- Git 中存在工作区文件，不等于已经有提交历史；检查提交、引用及真正保存的数据。
