# 镜像验证分层与判据

> 配置正确、编译成功、镜像内容正确、设备启动和外设可用是不同结论，应分别给出证据。

## TL;DR

- 先写判据，再选择最低成本且足以回答问题的验证层。
- 离线验收检查最终导出的镜像；中间 rootfs 不能证明分区、启动命令行或最终 initramfs 正确。
- 用故意错误的输入确认校验器会拒绝错误；避免只有正常路径的“全通过”。
- 未接设备、缺权限或缺工具是验证限制；没有独立阈值的测量作为观察记录。

## 各层能证明什么

| 层次 | 证据与判据 | 不能据此声称 |
| --- | --- | --- |
| 定义和选择 | manifest、板型/profile 契约、JSON schema、互斥组合 | 内核可编译或镜像可启动 |
| 编译与打包 | 固定源码、配置、成功退出、产物身份与摘要 | 实际启动用了该产物 |
| 离线镜像 | 分区、根分区选择、文件摘要、模块与 initramfs 一致性、账户与服务配置 | 固件、驱动或外设已在实机工作 |
| 设备启动 | 实际介质、运行内核、启动日志、根分区和使用的设备树 | 所有外设和电源路径都正常 |
| 功能与性能 | 按要求验证外设、恢复、功耗或启动终点 | 其他底板或软件版本也具有相同结果 |

## 本仓库已有机制

镜像检查器（工程源码：`tools/image_inspect.py`）的 `inspect_image()` 只读挂载最终
`.img` 的启动和根分区，调用 `inspect_files()` 比较项目内核、DTB/overlay、
启动配置和 initramfs 等契约，并确认命令行选择实际导出的 root PARTUUID。
这些检查覆盖静态一致性，不能替代实机启动。

输出中的镜像路径和 SHA-256 将报告绑定到受检查的文件。分享或部署前如果镜像再次改动，旧报告不再代表当前文件。内核产物报告（工程源码：`tools/kernel_artifact.py`）同样依赖产物摘要，文件名相同并不代表内容相同。

## 可迁移的工具设计

每项检查写清期望来源和失败条件。例如“所选板型不应包含另一底板的 GPIO 服务”来自板型隔离要求，而“启动应低于某秒数”需要独立的用户指标或基线，不能凭观察随意设定。

在正常夹具之外，分别替换一个摘要、移除一个必需文件、改变 root 参数或加入被禁止服务，确认检查会失败。反面对照应只改变与判据相关的一项，避免测试仅因无关解析错误而失败。

离线检查避免执行目标程序：目标架构可能不匹配，`--help` 也不能保证旧程序没有副作用。静态路径和参数字面量匹配只能当作弱证据；语义正确性仍需专门测试或受控运行。

区分结构化结果中的 `PASS`、`FAIL`、环境错误和未验证事项。计数或平均耗时是观察，只有相对于明确要求才成为判定。当前设备结果集中在[开发状态](../../project/status.md)，不要用历史实测填补本次未做的验证。
