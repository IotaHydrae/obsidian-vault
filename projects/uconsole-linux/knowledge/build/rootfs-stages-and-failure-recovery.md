# rootfs 阶段复用与失败恢复

> 阶段复用依赖输入身份和完成条件；失败后留下的目录不能当作成功缓存。

## TL;DR

- 区分下载缓存、编译产物、已配置 rootfs 和最终镜像，四者不能互相代替。
- 只有相关输入、输出和成功状态都匹配才能续跑；切板、切桌面必须使相应下游失效。
- 清理前检查挂载；卸载失败保留目录。补下载失败也不应删除原本可用的 rootfs。
- 这是可迁移设计；本仓库 Ubuntu 后端目前创建独立工作目录，不支持通用阶段续跑。

## 阶段契约

| 阶段 | 关键输入 | 完成条件 | 变化影响 |
| --- | --- | --- | --- |
| 基础系统 | tarball 版本/摘要、解包策略 | 解包成功、OS 身份匹配、元数据完整 | 所有安装与导出失效 |
| 用户态包 | 源、包清单、本地包 receipt、安装代码 | 安装/配置完成、依赖审计无未完成项 | 板级整合、镜像失效 |
| 板级整合 | board、内核包、DT/固件、服务 | 载荷与板型匹配、启动引用一致 | 当前镜像失效 |
| 导出 | rootfs、分区布局、导出器 | 最终文件系统检查与回执成功 | 压缩/分发材料重做 |

一个 done 文件至少绑定输入身份；文件存在和时间戳都不足以证明安装完整。
标记更新使用临时文件和原子替换，重跑前撤回旧状态，失败不能复用旧成功标记。
只有一项应用完成时，不能发布全部应用就绪状态。

## 失败恢复的顺序

1. 保留首个失败与日志，确定失败阶段及它拥有的临时资源。
2. 查看该 rootfs 子树的 mountinfo；不要沿 `/dev`、`/proc` 或嵌套 bind mount 删除。
3. 按依赖逆序卸载本次获得的挂载；失败明确报告并保留目录，不使用 lazy unmount 掩盖未释放资源。
4. 校验源输入和已安装状态；不确定时从干净 Base 重建，不能靠补写 done 修复。
5. 完成该阶段验收后再允许下游执行。

恢复命令不自动操作运行系统。rootfs 中 apt 的失败与宿主包状态分别处理。
用户要求重新构建 rootfs 也不等于授权卸载宿主依赖或修改物理存储。

## 下载、复用与环境隔离

补下载相同 tarball 只恢复下载缓存，不能把旧 rootfs 升级到新版基础系统。
重复压缩再解压同一 rootfs 会增加 IO；允许直接交接目录时仍须检查阶段身份与挂载。
需要跨主机迁移时，归档保留 numeric ownership、链接、ACL 和扩展属性，详见
[文件元数据](../rootfs/file-metadata-and-capabilities.md)。

并发构建不要共享同一可变 rootfs；APT 下载缓存可另设锁或按工作目录隔离。
切桌面时只修改菜单保存值不会清除旧桌面文件；必须执行拥有该安装行为的阶段。

## 本仓库连接点与验证

Ubuntu 后端（工程源码：`scripts/image_backends/ubuntu_base.py`）的 prepare/execute 分离输入快照与执行，
构建目录绑定 spec；execute 校验后创建新 rootfs，不会把失败目录自动判为完成。
文件导出器（工程源码：`scripts/image_backends/rpi_image.py`）检查 rootfs 子树无挂载再导出。

若将来实现续跑，测试应覆盖：受追踪输入变化使下游失效；仅补下载不误删状态；
故意安装失败不发布成功；切板后导出拒绝旧身份。现有机制见[输入身份](input-identity-and-cache.md)。
