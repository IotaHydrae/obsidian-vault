# Android 调优模块：从脚本通过到开机生效还差哪些验证

> 审查必须覆盖路径类型、启动顺序、错误处理、最终读回和持久回退；脚本语法正确不能证明运行逻辑和收益正确。

## TL;DR

- 分别证明代码会执行、执行成功、重启后保持以及业务有收益。
- 沿所有写入者追踪参数，系统 init 和遗留脚本都可能在模块之后覆盖设置。
- 有缺陷的前置检查可能屏蔽后续危险路径，不能修一行就立即运行整份脚本。

## 先检查入口和路径

zram 有两种不同对象：

```text
/sys/block/zram0       sysfs 目录／目录链接：读取 disksize、mm_stat 等属性
/dev/block/zram0       Android 上的块设备节点：应按实际设备布局确认
```

把 `/sys/block/zram0` 交给 `[ -b ... ]` 会把目录误当作块设备，导致提前退出。当前容量大于系统默认值，也不能说明该脚本设置成功：它可能来自手工操作或另一个模块。

`sh -n script.sh` 只解析语法，不执行脚本；它不会发现这类路径类型错误、无效条件或启动竞态。

## 沿启动顺序找最后一个写入者

检查模块的 `post-fs-data.sh`、`service.sh`，通用 `service.d`／`post-fs-data.d`，以及 ROM 的 init rc、fstab 和厂商服务。建立一张最小表：

| 参数 | 写入阶段 | 需要核实 |
| --- | --- | --- |
| zram 容量 | fstab／系统 swap 初始化、模块晚期脚本 | 哪次成功启用，后续是否重建 |
| `vm.swappiness` | 模块早期、`sys.boot_completed` 触发器 | 启动完成后最终值及实际写入者 |
| I/O 参数 | 模块与设备 init | 目标设备、覆盖顺序、读回结果 |
| CPU governor 参数 | 系统初始化、性能服务、模块 | 是否只是重复 ROM 默认值 |

Magisk 的 `post-fs-data` 是阻塞启动阶段；长等待会影响开机。晚期脚本即使有等待上限，超时后也必须明确退出，不能假装系统已就绪。具体时限按已安装 Magisk 版本核对。

## 重建 swap 的特殊审查

`swapoff → reset → 设置容量 → mkswap → swapon` 每一步都会改变系统状态。仅判断“已用 swap 小于某个数”不足以证明能安全执行：还要考虑可用 RAM、并发分配、回收和恢复能力。

审查时至少确认：

- 前置条件不满足时保持原 swap，不继续破坏现状。
- 每个命令都检查返回值，失败不打印成功。
- 成功后核对 `/proc/swaps`、设备容量和运行状态。
- 回滚也要检查结果；文件存在或恢复命令已发出不能代替有效状态。

2026-10-30 的审查发现路径类型错误使扩容脚本提前退出；后续重启读到约 1.06 GiB 的系统默认容量，并有脚本报错。该证据支持自启动失效，不证明此前一次黑屏的原因。缺少上一启动的有效崩溃日志时，保留原因未定。

## 持久回退与验收

手工把 sysfs 写回旧值只恢复当前状态；模块下次启动仍可能覆盖。持久回退还须停用对应模块或实际启动入口，保留备份和原权限，核对其他同类脚本。

| 层级 | 验收问题 |
| --- | --- |
| 静态 | 语法、路径类型、错误处理是否正确 |
| 当前运行 | 目标参数是否读回为预期值，业务是否正常 |
| 重启持久性 | 新启动后配置是否有效，日志是否明确，无覆盖冲突 |
| 收益 | 与基线相比是否改善目标业务，副作用是否可接受 |

按实际已完成的层级记录。模块停用标记已存在但尚未重启，只能证明配置了停用，不能声称重启验证通过。收益方法见 [调参验证](android-tuning-benefit-validation.md)。
