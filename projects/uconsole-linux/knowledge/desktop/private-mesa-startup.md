# 私有 Mesa 的启动收益与进程隔离

> 私有 Mesa 应覆盖实际使用它的桌面进程，并在启动普通应用前清理环境。

## TL;DR

- 固定发行版 ABI，只为目标 GPU 构建必要驱动，不替换系统 Mesa。
- 同时核对 labwc 和外壳库映射，防止把首次加载成本推迟到 Noctalia。
- CM4 顶栏缓冲曾提前约 1.6 s；这属于重启的软件边界，不是物理冷启动或首帧承诺。

适用于 Noble ARM64、CM4 V3D、labwc/wlroots 0.20.2、Noctalia 5.3.0；构建入口见 Noble Mesa 配方（工程源码：`image/packages/mesa-noble/README.md`）。

## 方法：固定时钟、缓存状态和可观察边界

FBO 观察来自合成器导入客户端缓冲时的 debug 日志，按当前固定输出下的
1280×69 顶栏和 1280×720 背景尺寸识别。它不证明已经扫描输出、内容完整或可交互；
壁纸纹理上传可能发生在首个缓冲之后。物理首帧仍需摄像、光电或用户观察等独立证据。
`systemd-analyze` 的 graphical.target 早于桌面外壳就绪，也不包含固件阶段。

首次改用新构建 Mesa 的暖会话曾出现 `queued surface rendering took 1494.2ms`，
后续共享样本已使用该构建积累的持久 shader cache。它揭示新镜像首次用户会话的
额外边界；没有逐项计时证据时，不能将全部延迟确定归因于 shader 编译。

本文的 A/B/A 验证了预热持久 shader cache 后的系统重启首会话。后续重复应继续记录
boot ID、实际库映射、调用耗时、缓冲边界、保护标志与异常，并固定探针和启动方式。
首次使用另用独立缓存目录比较，保留用户原缓存。不要混用暖会话、系统重启、
物理断电和新镜像首次启动来计算收益。

统一单调时钟可以避开设备墙钟跳变。探针与 debug 日志本身有开销，严格对照应覆盖
相同进程和调用；调用墙钟时间减去 CPU 时间还含调度等待，不能全部记作 I/O 等待。
约 0.52 秒的合成器 wrapper→探针构造函数间隔在三种配置下仍存在，属于另一个待测
加载边界；可以在紧邻 `exec` 前和构造函数中记录单调时间及 `getrusage` 差值，
无需因此重编完整图形栈。

## 从依赖加载到完整路径

系统 Mesa 首次 `dlopen("libEGL_mesa.so.0")` 约需 1.62 秒。ELF 依赖链为
Mesa EGL → Gallium → LLVM；该窗口的主要缺页与文件输入显著多于暖会话。
这些观察支持调查动态加载及其依赖，不能把全部等待归因于 LLVM 的某一个文件。

候选包从 Ubuntu `25.2.8-0ubuntu0.24.04.4` 固定源码和发行版补丁原生构建，
只保留 V3D/VC4、Wayland/EGL/GLES2/GBM，关闭 LLVM 与无关驱动及前端。
它安装到 `/usr/lib/uconsole/mesa-noble`，不替换发行版库，也不注册全局 GLVND
或 ldconfig 路径。固定配方、ABI 检查和包回执用于复用构建结果；构建成功不代表
显示正确或启动更快。

2026-10-22 的初步 `system-first-2` 与 `private-first-1` 暴露了成本转移：
仅给合成器使用私有库后，其 Mesa 加载从 1.625341 降至 0.042901 秒，Noctalia
进程从内核启动后 11.02 提前至 9.47 秒创建，但仍映射系统 Gallium/LLVM；
首个顶栏 FBO 从 13.276925 变为 13.494915 秒，没有提前。不能只凭合成器耗时
宣称桌面加速，因此后续将合成器和外壳一起纳入比较。

### 系统库首次加载的诊断基线

同 CM4/Noble 系统栈，用临时 preload 在同一单调时钟记录调用，构造函数清理环境以免传给客户端：

| 会话 | EGL 无显示扩展查询 | 其中 Mesa dlopen | eglInitialize |
| --- | ---: | ---: | ---: |
| 暖会话 | 0.073660 s | 0.073188 s | 0.005768 s |
| 重启首会话 1 | 1.641890 s | 1.636253 s | 0.010509 s |
| 重启首会话 2 | 1.625789 s | 1.619948 s | 0.009625 s |

第二次加载窗口的主要缺页 403、输入块 116696，按 Linux 512 字节单位约 56.98 MiB；
暖会话两者均零。依赖链为 Mesa EGL→Gallium→LLVM，文件大小不能冒充 RSS 或实际读取量，
墙钟减 CPU 也不能全算 I/O 等待。后续配对结果见下节；普通应用隔离见本文的进程边界。

复现时需区分 greetd initial session 与暖会话；`/run/greetd.run` 保证每次开机只执行一次初始会话。
诊断包装器放可执行文件系统（本机 /run 为 noexec），恢复原配置并删除临时 unit/timer/probe。
未测固件或物理首帧，原始调用记录在设备 `20261021/startup-profile/` 与对应本机缓存。

### 同条件 A/B/A 重启比较

随后按系统库 A → 两者私有库 B → 系统库 A 进行三次重启。各次使用相同合成器探针、
Noctalia 探针和直接 ELF 启动方式；包始终安装，Noctalia 探针构造函数临时代替包中
小型 helper 执行相同环境清理，改变的是私有库路径选择。两套持久 shader cache
已预热。同一 SD、用户配置、服务、输出 transform 270 与 scale 1.5 保持不变。

| 样本 | labwc 进程创建 | Noctalia 进程创建 | 合成器 Mesa `dlopen` | 首个顶栏 FBO |
| --- | ---: | ---: | ---: | ---: |
| `aba-system-1`，A | 7.65 | 11.08 | 1.625090 | 13.268221 |
| `aba-private-1`，B | 7.70 | 9.52 | 0.043198 | 11.656282 |
| `aba-system-2`，A | 7.76 | 11.14 | 1.618381 | 13.400653 |

单位为秒；进程创建与 FBO 时间起点为内核启动，调用列为耗时。`/proc/<pid>/stat`
的 starttime 按实际 `CLK_TCK` 换算。包装器通过 `exec` 保留 PID，因此进程创建
不等于实际 ELF 完成加载或应用初始化。

B 的首个顶栏 FBO 比前后 A 分别提前 1.612 和 1.744 秒。B 中两者均映射私有
EGL/Gallium/GBM，Noctalia 未映射 LLVM；A 中恢复系统库映射。Noctalia 的 Mesa
`dlopen` 在 A 中约 0.108 秒，B 中为 0.012266 秒。恢复 A 后的回退支持库选择影响
当前软件启动路径，但一次 A/B/A 仍不足以给出稳定节省值或长期可靠性结论。

三次 boot ID 依次为 `00000000-0000-4000-8000-000000000028`、
`00000000-0000-4000-8000-000000000009` 和
`00000000-0000-4000-8000-000000000008`。原始样本保留在开发机
`~/.cache/uconsole-desktop-20261018/mesa-noble-experiment/` 的同名 JSON 中。

两个系统基线加载窗口均有主要缺页 403、输入块 116696；私有合成器样本为 9 和
3176。Linux 此处输入块单位为 512 字节，分别约 56.98 与 1.55 MiB；它们是调用
窗口内进程的文件输入观察，不是包体积、RSS 或逐库读取归属。上述样本均无失败单元，
固件保护标志为零；这些状态不代替图形正确性验证。

## 将私有库限制在实际使用它的进程

合成器和外壳应分别显式选择库路径，普通应用继续使用系统库。不要把私有路径导出到
用户服务管理器或全局环境。合成器启动普通客户端和 Xwayland 时必须清除相应覆盖。

Noctalia 启动应用时可能继承自己的环境，因此仅给外壳设置 `LD_LIBRARY_PATH`
仍不足以隔离。当前方案在实际 Noctalia ELF 的加载环境中同时设置私有库路径和
一个小型 `LD_PRELOAD` 清理库；其构造函数清除 `LD_LIBRARY_PATH` 与
`LD_PRELOAD`。Noble 的 glibc 已缓存本进程初始搜索路径，稍后的 Mesa `dlopen`
仍可选中私有库，而之后 `exec` 的子进程得到清洁环境。

必须直接执行 `/usr/lib/uconsole/noctalia/bin/noctalia`。若先执行 `/usr/bin/noctalia`
这样的 shell 包装器，清理库会在 shell 中运行，真正的 Noctalia 反而失去私有路径。
该机制依赖已验证的 glibc 加载行为，不能假定适用于任意 libc 或其他启动包装器。

隔离的判据包含两层：用小型真实 ELF 测试本进程清理后 `dlopen` 与子进程 `exec`
的搜索结果；再从实际桌面启动普通图形应用，核对其环境和库映射。单独查看
`/proc/<pid>/environ` 不够：`unsetenv` 后该文件可能仍保留初始环境内存中的字节。
最终应观察子进程实际收到的环境及实际加载路径。

实际部署已使用包中的小型 helper，去掉测量探针。从 Noctalia 启动器选择临时测试
应用后，子程序记录的图形/加载器覆盖变量为空，EGL 查询成功，实际映射系统
EGL/Gallium/GBM 与 LLVM；两套桌面进程则映射私有 Mesa，不含 LLVM。
临时应用条目随后删除。相应证据为 `production-warm.json` 与 `client-isolation.json`。
合成截图保留横向壁纸和顶栏；私有 V3D 4.2.14.0 上，既有 241 组矩形 GLSL 对比
与原始着色器的 RGBA8 输出逐字节一致。这些验证覆盖相应软件输出，不替代肉眼
确认屏幕、菜单手感或完整应用兼容性。

随后不带探针重启，`production-final.json` 的 boot ID 为
`00000000-0000-4000-8000-000000000003`：两处私有库选择仍生效，横屏与 150%
缩放保留，合成截图正常，包校验与失败单元为空，固件保护标志为零。临时探针、包装器
和回滚定时器已移除；该轮只验证持久配置，没有继续计算 FBO 耗时。

## 硬件适用范围

库包按发行版、架构与运行时 ABI 复用，GPU 驱动选择按核心板能力决定。当前包只包含
V3D/VC4，实机证据仅覆盖 CM4。CM5 与兼容 CM 接口的 Rockchip 等核心板尚未验证；
不能因连接器相同而选择相同驱动配方。其他 GPU 应建立自己的驱动选择、依赖闭包和
受控渲染/启动证据，保留系统库与恢复路径。
