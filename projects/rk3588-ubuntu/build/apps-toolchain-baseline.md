# app 的工具链基线：交叉 vs 原生、以及"到底在哪编"

> 起因：一个常被混在一起的问题 —— "app 该在 x86 上交叉编，还是在板子上原生编？"
> 同一份基准的交叉与原生产物在所测负载中结果一致，性能差异取决于工具链与配置，
> 不能只按宿主架构判断。发布时选择与目标兼容的 sysroot，并验证 ISA、动态库与运行行为。
> app 的目录约定、安装与缓存契约见 [apps.md](apps.md)。

## TL;DR

- 同一份源码、同样 `-O2`，x86 交叉（gcc 15.2 + sysroot 2.43）vs 板子原生（gcc 13.3 + 2.39）：
  **四个变体 checksum 全相同**；差别只在 **GLIBC 门槛**（交叉 2.38 / 原生 2.34）与
  静态体积（差 10.1%，因为 2.43 的 `libc.a` 更大）。
- 性能**逐处不同、方向不定**（该基准总耗时 +3.6%），不能推出交叉编译对全部应用的性能影响。
- 结论：**别用开发机（Ubuntu 26.04，sysroot 2.43）出产物**；要么板子原生、要么编译服务器交叉（基线 == 镜像）。
- rootfs 在 ARM64 主机执行可避免 QEMU；历史 `rootfs` 阶段端到端记录为 7.4–7.7×，包含下载与 I/O，
  见[测量范围](build-speed-comparison.md)，不代表应用编译倍率。
- 当前 apps 阶段只编 C，Rust 使用固定 deb；显式 Rust 发布包仅在 noble arm64 板生成，见 [Rust deb](rust-app-debs.md)。

## 1. 实测 A/B（2026-09-14）

同一份源码（`tests/optbench.c`）、同样 `-O2`，两边各编一份，在开发板上钉 `cpu4`(A76) 跑 5 轮×内部 3 次
取最小值再取中位数：

| 变体 | 工具链 / 链接 | 体积 | 最高 GLIBC 需求 | 中位总耗时 | vs 交叉 |
| --- | --- | ---: | ---: | ---: | ---: |
| `cross-dyn` | x86 交叉 **gcc 15.2** / 动态 / sysroot **2.43** | 72,280 B | **2.38** | 74.2 ms | — |
| `native-dyn` | 板子原生 **gcc 13.3** / 动态 / **2.39** | 72,136 B | **2.34** | 76.9 ms | **+3.6%** |
| `cross-st` | x86 交叉 15.2 / **静态** / `libc.a` 2.43 | 597,920 B | — | 68.7 ms | −7.4% |
| `native-st` | 板子原生 13.3 / **静态** / `libc.a` 2.39 | **537,664 B** | — | 75.1 ms | +1.2% |

四个变体的 **checksum 全部相同**，说明这些基准负载的结果一致。结论限定在该源码、选项和目标板：

1. 都是 `aarch64-linux-gnu`、LP64，默认选项也相同（`-march`/`-mcpu`/`-mtune`
   均为空 = generic armv8-a，`-moutline-atomics` 与 `-mfix-cortex-a53-843419` 两边都 enabled）
   交叉编译本身不要求在目标板模拟执行，也不决定最终应用性能。
2. **差别在编译器版本 + sysroot 基线**：
   * **GLIBC 门槛不同**：交叉版要 `GLIBC_2.38`、原生版只要 `2.34` —— 根源是 **GCC 15 默认 `-std=gnu23`**，
     `atol/strtol` 变成 `__isoc23_*` 符号（2.38 才引入）。同一份源码，**交叉版对目标机的 glibc 要求更高**。
   * **静态体积差 10.1%**（597,920 vs 537,664 B）：静态把 libc 编进去了，2.43 的 `libc.a` 比 2.39 大。
   * 动态体积几乎一样（差 144 B / 0.2%）。
3. **性能逐处不同、方向不定**（原生相对交叉）：`call_overhead` **+33.4%**（15.2 在间接调用点内联了那个小函数，
   13.3 没有）、`vec_f32` +14.1%、`arith_ilp` +12.5%，而 `vec_i32` −6.5%、`ptr_chase` −4.0%，其余 ±2% 以内
   该基准总耗时 +3.6%；这不是整机或实际应用的性能变化。
4. 发布选择与目标兼容的工具链 / sysroot，并在目标板验证；相同发行版有助于减少错配（§2）。

⚠️ 做这个 A/B 时才发现 `alloc_free` 之前的数字是假的（`malloc/free` 对被 GCC 15 整体删除），
修法与证据见 `tests/README.md`「这个脚本自己的三个坑」。

## 2. 那"app 到底在哪编"？（决策）

先把两件事分开 —— 它们经常被混成一件：

| 阶段 | 做什么 | 在哪跑 | 理由 |
| --- | --- | --- | --- |
| `rootfs` / `board` 阶段（rootfs 与板卡配置） | apt/dpkg、overlay、安装 app 及内核 / U-Boot 产物 | **ARM64 构建机** | 原生执行目标用户态；`board` 阶段是安装 deb，与编译倍率无关 |
| 内核 / U-Boot 编译（镜像阶段之外） | 编译并打包 deb | **编译服务器** | 历史记录约快 6–9×，见 [build-speed-comparison.md](build-speed-comparison.md)；交叉编译器在宿主原生运行 |
| apps（独立准备阶段） | 校验 Rust 固定 deb、编译 C app 并记录状态 | C 构建使用**与镜像兼容的工具链基线** | 默认无需 Cargo/rustc；仍须验证目标 ISA、库依赖与运行结果 |
| Rust deb 发布（显式命令） | 真实编译、打包并更新 manifest | **Ubuntu noble arm64 板** | 原生目标库生成依赖；源码和包摘要匹配后才能复用 |

所以"rootfs 整体在 RK3588 上编"是对的，但**理由不是 gcc**，而是 apt/dpkg 在 qemu 下太慢；
**内核/U-Boot 反过来应该在编译服务器上编**。

显式源码开发与 C 产物的三种工具链选择如下；Rust 正式 deb 发布遵循上表限制：

1. **板子上原生**（`gcc 13.3` + 本机头/库 `glibc 2.39`）：与 noble 镜像基线一致，减少 glibc 错配；
   编译耗时取决于依赖、并行度与缓存，且**要先在板子上装编译工具**
   （镜像是刻意不带 gcc 的；`apt-get install -y gcc make`，属"构建机依赖只装干活那台"）。
   还须验证目标 ISA、动态库依赖与实际运行行为，不能仅由发行版相同推定全部兼容。
2. **编译服务器交叉**（`gcc 13.3` + sysroot `glibc 2.39` == 板子）：采用相同验证要求，且与内核/U-Boot 同一条流水线；
   产物用 `sync-to-board.sh --artifacts` 推给板子（会带上 `build/apps/`）。
3. ⛔ **开发机（Ubuntu 26.04，交叉 `gcc 15.2` + sysroot `glibc 2.43`）出产物**：**只适合验证"能不能编过"** ——
   动态版可能引用板子上没有的 `GLIBC_2.4x`；静态版则把镜像里从未存在过的 2.43 `libc.a` 编进去。

> `rootfs` 阶段对 C 使用 `make install-only`，对 Rust 用 apt 安装固定本地 deb，不会补编。
> 普通源码同步包含 Rust deb 与 manifest；C 产物与 `.build-state` 另用 `--artifacts` 同步。
> 默认构建与 `--from=rootfs` 会先准备 apps；缺失或过期包提前拒绝，不回落 Rust 编译。完整契约见 [apps.md](apps.md)。
