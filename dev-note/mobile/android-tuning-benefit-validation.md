# Android I/O 和显示调参：怎样验证收益

> 参数读回正确只证明设置生效；性能和续航结论需要与真实工作负载相匹配的对照测量。

## TL;DR

- I/O 先找实际文件系统与块设备层，测试方法必须覆盖所声称的机制。
- `wm size` 的逻辑分辨率、应用渲染缓冲区和面板模式分别确认。
- 采用交错对照，记录温度、缓存、供电和副作用；无稳定差异就保留“收益未证实”。

## I/O：先确认测量层

`/data` 可能经过 device-mapper 指向底层 UFS 设备。物理设备的预读值改变，不代表上层 dm 设备相同，也不证明应用实际读取变快。

| 做法／观察 | 能支持的结论 | 缺少的证据 |
| --- | --- | --- |
| 修改 scheduler 并读回 | 该设备选择了此调度器 | 实际应用的时延、吞吐、能耗 |
| `read_ahead_kb` 增大 | 此队列的预读参数变化 | 目标读取路径是否受益 |
| `nr_requests` 写入命令成功 | 发出了写入请求 | 读回是否接受该值、队列行为是否改变 |
| 只读 `O_DIRECT` 短测 | 该直接 I/O 路径的有限观测 | 页缓存预读、写入、应用启动和长期能耗 |
| 关闭 `iostats` | 减少部分统计采集 | 性能收益；同时会损失排障数据 |

不能仅凭 UFS／SSD 介质就断言某个调度器必然更好。可用调度器与含义随内核版本变化；旧 Android 内核的 CFQ、deadline 不能直接套用现代 blk-mq 的调参建议。

## 显示：三个尺寸分开测

```text
wm size／density 覆盖 → 应用布局和渲染缓冲区 → 合成／缩放 → 面板物理模式
```

1440×3120 改成 1080×2340，逻辑像素数为原来的 `0.75² = 56.25%`，减少 43.75%。这只是几何结果；面板仍可能按原生分辨率和 90 Hz 扫描。系统总功耗还取决于亮度、刷新率、内容、CPU/GPU、无线与温度，不能把像素降幅当省电比例。

`wm size`／`wm density` 看逻辑覆盖，显示服务看物理模式；需要解释渲染负担时再核对目标应用的实际缓冲区。`gfxinfo` 一段滚动没有报告 jank，不代表所有应用都无卡顿，也不等于实际测到 90 fps。

## 设计有区分度的对照

1. 定义目标：例如同一应用启动时间、同一列表滚动帧耗时或相同任务的电量消耗，先选与目标匹配的测量。
2. 固定应用版本、任务输入、网络、亮度和刷新率，记录温度、供电、缓存与编译状态。
3. 用 A→B→B→A 等交错顺序，并按任务特点区分冷启动和热缓存，避免把升温或缓存变化当成参数收益。
4. 保存单轮结果和差异，不只保留最快一轮。没有稳定差异时说明测量不足或收益未证实。
5. 检查文字清晰度、布局、触控、应用重载和后台功能等代价。

2026-10-20 的案例中，九次 64 MiB 只读 direct 短测波动较大，不能证明 I/O 调优提升日用性能。1080p／1440p 设置页滚动均未报告卡顿，仅支持该轻负载场景没有观察到差异，续航仍未测量。

## 恢复与边界

恢复到测试前记录的覆盖值和 I/O 值；测试前已有覆盖时，盲目执行 `wm size reset` 不等于恢复原状态。还要核查 [开机脚本是否会重新覆盖](android-tuning-module-audit.md)。

充电调试窗口不用于估计灭屏待机续航，参见 [耗电测量边界](android-thermal-and-battery-diagnostics.md)。
