# CM4 提前显示：在冷插拔枚举结束前预加载现有模块

> 提前加载现有显示依赖可让 DRM 更早注册，但不直接证明实体画面更早。

## TL;DR

- 优先使用 CM4 精确模块闭包，保持驱动字节和根挂载路径不变做对照。
- 已观察 `vc4drmfb` 从 7.918 s 到 5.082 s；桌面和物理首帧需另测。
- initramfs 和内建驱动属于后续独立变量，不应同时更改后混算收益。

## 方法：保持驱动不变，只提前请求模块

测试配置为 CM4 Rev 1.1 uConsole、SD 卡根分区和 `6.18.57-v8-uconsole`。
两次启动都使用同一套私有 V3D Mesa 合成器试验版本；普通应用使用系统 Mesa。
试验唯一新增项为 `/etc/modules-load.d/uconsole-display.conf`，按以下顺序请求加载模块：

```text
i2c-brcmstb
ocp8178_bl
panel-cwu50
vc4
```

## 根分区挂载前必须考虑的源码依赖

目标配置与原始内核产物 `17e83bbc8a6a21cc` 一致。
DRM/VC4、面板、背光及其辅助组件均为模块。GPIO-I²C PMIC 总线、稳压器、GPIO/pinctrl、
mailbox 接口、电源域和所需时钟均已内建。正在运行的面板模块来自原始产物中的驱动；
其字节与后来维护的补丁不同。测试初始化顺序时，应保留这一软件身份。

已启用的 HDMI 组件还需要 `CONFIG_I2C_BRCMSTB=m` 提供 DDC。
若适配器不存在，`vc4_hdmi_bind()` 会返回 `-EPROBE_DEFER`。
这是设备树依赖，因此不在 VC4 基于符号关系得到的模块依赖闭包中。
即使当前配置重点使用 DSI，也必须包含该 DDC 模块。

四个入口模块的递归 `modules.dep` 依赖闭包包含 19 个模块，
其中包括 DRM/背光、CEC 和 ALSA 辅助模块。加上 VC4 的 Kconfig 所选择的 HDMI codec 后，
得到包含 20 个模块的候选集合。目前其 `.ko.xz` 文件合计 633,224 字节，
未压缩模块合计 3,213,400 字节。这并不是 initramfs 的大小。
加载器、`/init`、库和模块元数据还会增加空间占用。
在检查过的路径中，VC4、CWU50 和 OCP8178 均未声明外部固件文件；
此处对 Raspberry Pi 固件的依赖是 mailbox 接口。

面板探测必须取得稳压器、复位 GPIO 和背光。VC4 必须注册 DSI 主机、挂接面板，
并完成组件绑定后，显示才能使用。在运行中的源码里，根据所选路径不同，
面板驱动的显式延时总计约 280–440 ms；这些延时无法解释根分区挂载后的全部延迟。
对照启动中没有此前黑屏时的 DSI 超时，不能再用那些超时解释当前的启动延迟。

## initramfs 与内建方案

最小显示 initramfs 可以在挂载根分区前加载依赖闭包，并绘制固定图像或控制台。
移除现有完整 initramfs 在固件阶段节省了约四秒，但这不是最小显示 initramfs 的实测开销。
构建后应比较从复位到首个实际可见画面的总时间；仅有更早的模块时间戳并不足够。

将显示依赖闭包内建进内核，可以保留直接挂载根分区的启动方式，并有可能在用户空间启动前完成初始化。
它会增大固件加载的内核，并将同步 probe/prepare 工作提前。
两种方案都需要单独测量，并保持驱动实现和供电/复位状态完全一致。
Plymouth/控制台内容、横屏方向和实体屏幕是否可见，与 DRM 注册是不同的验证项。
桌面不会在 initramfs 内运行。

## 设备观察：注册时刻提前，桌面收益未建立

| 观察项 | 对照 `c35193d1` | 静态加载试验 `38524b95` |
| --- | ---: | ---: |
| `/sbin/init`，原始内核时间 | 1.817 s | 1.777 s |
| 面板探测 | 7.678 s | 4.694 s |
| `fb0: vc4drmfb` | 7.918 s | 5.082 s |
| modules-load 进程 | 4.407–4.518 s | 4.382–5.095 s |
| sysinit 目标，内核运行时间 | 7.378 s | 7.523 s |
| systemd 总时间 | 14.800 s | 15.035 s |
| 首张经人工确认的完整桌面截图，内核运行时间 | 17.62 s | 18.57 s |

四项加载请求全部成功。试验保留了 Wi-Fi/SSH、横屏 transform 270 和显示电量的指示器；
采集的失败单元列表为空，降频状态报告为零。合成后的画面中，壁纸/图标先于完整桌面面板出现。
由于采样方式和各次运行的波动，不能将桌面截图时间之差归因于固定的启动开销。

工程只在选择 CM4 uConsole overlay 时安装这份精确的四行配置。
CM5 和通用 CM4 底板保留各自的策略。镜像检查工具会拒绝正式 CM4 配置缺失或被更改的情况。
`systemd-modules-load` 排在 sysinit 之前，但与 udev 冷插拔枚举并行运行。
它增加的同步探测工作可能影响关键路径；没有新增 Plymouth 启动顺序覆盖或 udev-settle 依赖。

观察结束后，临时安全定时器移除了试验文件。因此，随后的 PCIe 试验不能证明此次预加载配置持续存在。
之后已禁用这些定时器，并恢复工程规定的精确配置；其后续验证记录在
[启动时间记录](../boot/cm4-boot-time.md)中。

## 证据与源码定位

私有证据位于 `~/.cache/uconsole-cm4-postflash-20261018/optimization-round3/`：
其中包含 `boot-mesa-private/` 的原始内核日志、`boot-early-display/` 的观察/详情，
以及之后的配置归一记录。内核早期事件使用原始 `dmesg`；
journal 收录日志时的时间戳不适合计算这些时间间隔。

相关的固定版本/准备后的源码为 `drivers/gpu/drm/vc4/Kconfig`、
`vc4_hdmi.c`（DDC 适配器查找）、`vc4_dsi.c`（主机挂接/组件绑定）、
`drivers/gpu/drm/panel/panel-cwu50.c`（probe 和 prepare），以及
`arch/arm/boot/dts/broadcom/bcm2711.dtsi`。
此次试验以原始产物的配置及准备后的源码为准，不能仅依据较新的驱动补丁界定。
