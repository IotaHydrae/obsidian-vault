# 编译分发（把局域网机器变成编译节点）—— **已立项，暂不做**

> 起因（2026-09-26 用户）："我记得有个工具可以把局域网内的电脑都变成编译节点，加速 C 文件编译。"
> 用户决定：**先立个项，等有时间再研究**（本文就是那个项）。

## TL;DR

- 结论：**现在不做**（理由有实测数字支撑，见 §3）。
- 可选工具见 §1；我们自己的实测数字（决定"值不值得做"）见 §2。
- 将来什么条件下再评估、按什么顺序做，见 §4。
- 注：本文只是**立项记录**；真正落地的那部分（icecc）见
  [icecc-distributed-build.md](icecc-distributed-build.md)。

## 1. 可选工具

| 工具 | 形态 | 说明 |
| --- | --- | --- |
| **`distcc`** | 无中心，客户端把编译任务发给 `DISTCC_HOSTS` 里列的主机 | 老牌；`pump` 模式把预处理留在本机、远端只要有编译器；**所有节点必须同一套工具链 + sysroot**；内核可用 `make CC="distcc aarch64-linux-gnu-gcc"` |
| **`icecc` / Icecream**（SUSE） | **中央 scheduler + worker**，worker 自动加入、自动分发环境、带本地缓存 | distcc 的进化版，**"一台强机 + 若干普通机"这种形态更合适**；SUSE 自己用它发版 |
| `ccache` | **本地**缓存（不分发） | 零风险、和上面二者可叠加；跨内核版本/改动重复时命中率高 |
| `sccache` / `sccache-dist` | 本地缓存 + 实验性分布式 | 主要面向 Rust/C++（MSVC/clang）；生态不如 icecream 成熟 |
| `mold` / `lld` | 链接器 | 只加速**链接**（我们内核构建里链接确实占不小比例，见 §2） |

## 2. 我们现在的实测数字（决定"值不值得做"）

（2026-09-26，24 核 x86_64 服务器交叉编 arm64）

| 场景 | 耗时 | 其中"编译"占多少 |
| --- | --- | --- |
| 改一个 `.c` 后增量 `-k` | **32 秒** | 只有 1 个 `.o` 编译（<1 秒），其余是 **vmlinux 重链 + `bindeb-pkg` 打包** |
| 无改动重跑 `-k` | **41 秒** | 同上（不重编任何 `.o`） |
| 全量 `-k` | **3.7 分钟** | 1995 个 `.ko` + 2360 个 `=y` |
| **`rootfs` 阶段** | **分钟级**；服务器上走 qemu 时实测 **46m57s**（同参数下板子原生 **6m04s**，快 7.7×） | ⛔ **完全不是编译**：是 `apt`/`dpkg` 的 IO + 依赖解析 + qemu 转译 |
| `rootfs` 阶段在 RK3588 开发板原生编 | **6m04s**（干净重建 + WiFi 下载）/ **2m14s**（apt 缓存热） | 同上，只是没有 qemu 的放大（数据见 [build-speed-comparison.md](build-speed-comparison.md)） |

## 3. 结论：**现在不做**，理由是有实测依据的

1. **编译分发只对"编译是瓶颈"有效**。我们现在的瓶颈是 ① `rootfs` 阶段 的 apt/dpkg + qemu（非编译）、
   ② 内核的**链接 + deb 打包**（也不是编译）。增量内核构建 32 秒里真正的编译不到 1 秒。
2. 于是 `rootfs` 阶段 的正解是**在原生 arm64 上编**（已定：rootfs → 开发板；内核/u-boot → 服务器 x86_64 交叉），
   icecream 帮不到这一块。
3. 异构环境的额外成本：LAN 分发要求**所有 worker 用完全一致的交叉工具链**
   （gcc 版本、头文件、sysroot）。我们手上是 x86_64 服务器 + arm64 开发板/工程机，
   要先把同一版 `gcc-aarch64-linux-gnu` 三台都装齐，否则会出现很难查的编译差异。
4. 内核这类"大量小文件 + 交叉编译"的负载，distcc 的预处理/传输开销经常吃掉收益
   （Icecream 好一些）；只有在**反复做全量构建**时才有明显账算。

## 4. 将来怎么评估（触发条件 + 顺序）

- **触发条件**：要反复做**全量内核构建**（例如大批量改 config 做模块裁剪），
  或者出现大型 C/C++ 工程（比现在的 `apps/` 重得多）成为构建瓶颈时。
- 顺序：**① `ccache`（零风险，先上）→ ② 量一次全量构建的"编译 vs 链接 vs 打包"占比 → ③ 再上 `icecream`**
  （中央 scheduler 放服务器，worker 放 服务器 + 开发板 + 工程机，统一一版 aarch64 交叉工具链）。
- 判断口诀：**"编译是不是瓶颈"** —— 不是就先别上。工具装好了不 profile 就上，收益会被网络与原语开销吃掉。
