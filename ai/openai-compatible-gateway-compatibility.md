# OpenAI 兼容接口：按协议层验证网关兼容性

> 相同的 API 地址形式不保证消息、流式事件和工具调用兼容；先确定协议，再逐层测试，桥接只修复已确认的差异。

## TL;DR

- 记录基础地址、模型 ID、认证方式、Chat Completions 或 Responses 协议。
- 模型列表和连接测试成功，不等于多轮、工具、图片与流式输出都可用。
- 重试和格式修正必须保留错误语义，不能把截断或失败伪装成正常完成。

## 兼容性检查表

| 层次 | 检查内容 |
| --- | --- |
| 地址与认证 | 基础 URL 与最终路径如何拼接，授权发给哪个服务 |
| 请求结构 | 消息角色、字符串或内容数组、图片表示、工具定义与结果 |
| 普通响应 | 字段类型、空值与缺省字段、错误体、结束原因 |
| 流式响应 | 事件边界、增量拼接、终止与异常状态 |
| 应用行为 | 多轮上下文、工具副作用、断线重试和展示逻辑 |

第三方服务支持哪些能力，以它的实现及实际测试为准；不能因其自称“兼容”就假设支持全部 OpenAI 行为。改变配置后用真实业务发起新请求，并核对实际选择的提供商与协议。

## SSE 桥接的关键点

- SSE 事件与 TCP 读取块没有一一对应关系；一个事件可被拆成多次读取，一次读取也可包含多个事件。
- 增量解析要保留跨块缓冲、换行和 UTF-8 边界，按事件而不是按单次读取处理 JSON。
- Chat Completions 与 Responses 的事件模型不同；修改 URL 不构成协议转换，不能混用终止判据。
- 对 optional 字段的 `null`、缺省或空数组，只按相应协议和客户端约定规范化；不能任意改写内容、使用量或工具结果。
- 区分正常结束、输出长度限制、拒绝、未完成和传输中断；不要在连接断开时补造“正常结束”。

## 重试边界

记录每次尝试的请求 ID、起止、是否收到响应头、首个事件和终止状态。客户端与桥接都重试时，次数和等待可能放大；部分内容已展示或工具可能已执行时，重新提交还可能重复产生内容或副作用。

请求级去重、工具调用去重和事务幂等由应用明确设计，不能假定上游都会提供相同能力。日志只需支持时序和状态诊断，无需保存完整密钥或全部对话。

## 验证顺序

先测试最小普通请求，再测试真实分片的流式回复、多轮、工具调用、图片及中断/错误。为桥接增加离线夹具，覆盖事件拆分、多个事件合并、空字段、非正常终止与取消；然后再做小范围端到端验证。
