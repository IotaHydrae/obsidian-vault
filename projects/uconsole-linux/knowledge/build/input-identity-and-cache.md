# 构建输入身份与阶段复用

> 只有产物文件存在，不能证明它对应当前选择；复用必须以完整输入身份和成功完成状态为依据。

## TL;DR

- 记录板型、系统、桌面、固定上游、配置、构建器和包的内容摘要；检查实际产物而非文件名。
- 下载缓存只减少传输，不替代包摘要、依赖解析和安装检查。
- 阶段失败先撤销旧完成状态；全部必需动作成功后才发布新状态。输入变化向依赖它的下游传递失效。
- 本文后半部分是设计原则，不表示工程已经实现可续跑的阶段缓存。

## 本仓库已有机制

上游检查（工程源码：`tools/upstreams.py`）的 `check_definitions()` 核对
`manifest/upstreams.env`、`.gitmodules` 与 Git index 中的 gitlink。checkout 校验另外确认实际提交，不能把空目录当作已固定源码。

内核产物加载器（工程源码：`tools/kernel_artifact.py`）的 `load_kernel_artifact()` 校验
构建报告及其声明的产物摘要；镜像不能仅因某个 `.deb` 存在就认定它属于所选板型。

Ubuntu Base 后端（工程源码：`scripts/image_backends/ubuntu_base.py`）的 `prepare()`
将 profile、recipe、内核报告、输入文件摘要及构建器/导出器摘要写入构建 spec；
`execute()` 在使用前重新核对关键摘要。工作目录身份用于区分输入，当前流程拒绝覆盖已有工作目录，并不据此跳过已完成 rootfs。

`download_verified()` 在复用或完成下载时校验固定 SHA-256。导出结束后记录最终
`.img` 摘要和包版本清单，便于比较设备或镜像使用的实际输入。

## 可迁移的阶段设计

若未来引入续跑，先为每个阶段写清输入、输出和完成条件。例：系统包安装的状态依赖包清单、源配置和安装逻辑；镜像导出还依赖分区布局、启动文件与导出器。

完成记录应包含输入身份及输出摘要。重建前撤销旧记录，避免失败后旧标记仍可复用；新记录先写临时文件，全部检查成功后再原子替换。单项应用编译成功不能发布“全部应用就绪”的状态。

失效按依赖关系传递：rootfs 输入变化使其后的板级整合和镜像导出失效；只补下载且已解包内容未变，不必撤销无关结果。切换板型必须使板级包和启动载荷重新匹配，不能沿用另一板型的完成标记。

缓存 `.deb`、编译缓存与“已安装 rootfs”分别建模。缓存命中仍需要校验，已安装状态还需覆盖安装清单和配置逻辑。可变软件源意味着固定 Base tar 不等于整个 rootfs 可逐字节复现；需要更严格复现时另行设计软件源快照与版本锁定。

## 验证边界

测试判据应来自上述依赖契约：修改一个受追踪输入后旧状态必须失效；注入中途失败后不得留下可复用完成记录；相同输入和有效产物可以复用。测试用隔离夹具验证这些行为，不通过执行真实镜像构建或刷机来验证缓存状态机。

当前代码依据见上述源码链接；这些源码事实不构成设备启动观察。离线与设备验证的区别见[验证分层](verification-layers.md)。
