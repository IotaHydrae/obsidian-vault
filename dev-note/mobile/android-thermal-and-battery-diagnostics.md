# Android 发热和耗电：怎样确定观测窗口与温控层

> 先把应用负载、内核温控、框架报告和电池供电窗口分开；温控状态为 0、闹钟次数多或电池温度高，都不能独立定位根因。

## TL;DR

- 结合一段时间的 CPU、进程树和同条件前后对照定位持续负载。
- Thermal HAL 未就绪时，框架的正常状态缺少完整解释力；继续查内核与厂商服务。
- 充电、USB 调试与亮屏窗口不能代替真实灭屏待机测量。

## 先找持续负载

记录故障时间、前台任务、是否充电、网络和温度来源。对照 `dumpsys cpuinfo` 的采样窗口、进程树与重复 CPU 样本；第一帧 `top` 可能包含诊断命令的扰动，单帧排名不能代表长时间耗电。

一个应用的初始化／子进程持续繁殖，比“后台应用很多”更有诊断价值。2026-10 的案例中，移除一个持续运行大量初始化进程的应用后，后台进程退出、CPU 和电池温度均下降，支持该负载参与发热。CPU 降低后的温度变化有滞后，也受环境与充电影响，不能照抄成固定降温幅度。

先识别进程归属和用户需要，再决定停止服务或处理应用；不要用批量禁用输入法、推送或 VPN 来制造更好的空闲数字。

## 温控至少分三层

| 层 | 看什么 | 判断边界 |
| --- | --- | --- |
| 传感与内核 | thermal zone 类型、温度、cooling device、mode | 节点存在不等于所有保护路径均正常 |
| 厂商用户态 | thermal-engine 等进程、init 定义、配置和事件 | 同名双进程需要核查来源，不能直接删掉一个 |
| Android 框架 | `dumpsys thermalservice`、HAL ready、缓存、状态 | HAL 未就绪且缓存为空时，状态 0 不能证明没有热压力 |

电池温度不等于 CPU／GPU 温度。节点名、单位和阈值须按驱动／接口核对；不能把另一机型阈值用于当前设备。

重复 thermal-engine 与 HAL 未就绪在同一 ROM 出现，只能证明两个异常现象并存。需要追踪服务声明、接口注册和故障时事件，才能解释两者是否相关。保持保护机制工作，以对照和日志定位。

## 续航测量要检查真正的供电时间

`batterystats` 总运行时间、on-battery、screen-off on-battery 和放电量必须配套。例：统计覆盖约 55 分钟，但电池供电仅约 9 秒、灭屏电池供电为零，就不具备估算待机每小时耗电的有效窗口。

- 不把启动以来 USB／充电唤醒锁的累计时长算成应用待机漏锁。
- `RTC_WAKEUP` 回调次数不等于设备实际从深睡唤醒的次数；还需实际睡眠状态和同窗口能耗。
- 任务名、Google 内部框架名不能直接当成另一应用或恶意进程的归属证据。
- Doze 的行为与充电、屏幕和运动状态有关；默认资源、运行时覆盖和 Java 兜底值也可能不同，先查实际解析出的有效值。

建立自然断开充电、无 USB 干扰的使用／待机窗口，记录亮屏、信号与后台工作，按相同条件比较；不为获取漂亮数字随意重置用户统计或改变业务功能。

## 验证与恢复

调整一次只针对一个有证据的负载或配置，验收原任务、通知、输入和联网。恢复时还原具体服务／设置及原值。供电量级异常时先查 [电流单位](android-battery-current-units.md)，不要据错误读数计算能耗。
