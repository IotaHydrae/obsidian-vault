# iOS 视频挂断后无响应：watchdog、Jetsam 与系统事件怎样对齐

> watchdog 证明应用未及时完成生命周期工作，不能独自判定应用 bug、温控降频或整机硬件故障；根因需要同一时间窗口的系统证据。

## TL;DR

- 记录挂断、开始卡住和恢复时刻及侧边键响应，统一日志时区。
- 按报告类型读终止原因，区分 watchdog、内存终止与仅记录的资源事件。
- 将温控、电池与系统界面服务作为待验证方向；更新或关闭保护机制都不是已有证据支持的修复。

## 先固定复现条件

在应用和系统版本、网络、亮度、充电等条件不变时复现，记录可观察事实：视频是否流畅、挂断后是否只卡当前应用、侧边键能否及时锁屏、何时恢复。

若要验证热量参与，再做自然冷却、不充电等有明确目的的对照，避免同时修改多项设置。即使热机更容易出现，也不能据此确定唯一根因；恢复响应与故障时刻必须对应。

正常信任配对可读取设备允许导出的诊断；这不等于能任意查看应用私有数据或修改温控。Root／越狱、普通侧载和诊断配对属于不同权限机制，不能把安装普通应用当成取得系统权限。

## 日志分类决定能回答什么

| 报告／字段 | 可以证明 | 常见误判 |
| --- | --- | --- |
| `0x8badf00d` watchdog | 应用超出系统允许的响应时限，被终止 | 当作已查明死锁、发热或硬件故障 |
| `scene-update`／`scene-create` | 界面更新／创建阶段超时 | 将任何该栈都认作视频挂断回调 |
| `FRONTBOARD` namespace | 系统执行相应的应用生命周期终止 | 认定 SpringBoard 本身崩溃 |
| Jetsam 进程条目的 `reason` | 哪个进程被内存机制终止及原因 | 把 `largestProcess` 当成被杀进程或罪魁 |
| wakeups／diskwrites 的 `Action taken: none` | 报告记录了资源事件，但未采取该终止动作 | 把报告文件存在当作应用崩溃 |

Jetsam 中的 `per-process-limit` 指该进程超过其限制，不直接证明整个设备物理内存耗尽。若用页数换算字节，应采用该报告的 `pageSize`，不能写死 4 KiB。

## 主线程快照怎样使用

- `mach_msg`／系统服务调用：支持当时处于等待路径；不能单凭一个栈证明服务永久死锁或硬件坏。
- `pread`：支持当时进行文件读取；未符号化的应用栈不足以说明文件内容，更不能据此诊断存储损坏。
- wall-clock timeout 与应用 CPU 时间要分开。等待也会耗尽墙钟时限；多核累计 CPU 时间又可能超过单核直觉。

完整记录报告内时间戳与时区，文件名时间可能是生成时间。不同日期的 SpringBoard Jetsam、内存压缩或温控事件可作为历史线索，不能直接填补当前故障现场的空白。

## 两个相邻超时的实例

iPhone X／iOS 16.7.16／微信 8.0.78，2026-11-01，北京时间：

| 时间 | 观察 | 结论边界 |
| --- | --- | --- |
| 21:38:57.7746 | `scene-update` 超过 10 秒，主线程等待系统界面／传感器服务路径 | 确认应用无响应；不确定完整整机卡顿原因 |
| 21:39:39.5840 | `scene-create` 超过 13.72 秒，主线程顶部 `pread` | 重新创建界面也超时；未证明具体读取或设备故障 |

同日 20:27 的 Jetsam 虽写 `largestProcess=WeChat`，实际被终止的是 `coreduetd`。20:33 的微信 wakeups 报告为 `Action taken: none`。两者都不能替代 21:38–21:39 现场的因果证据。

这组资料选取并成功解析 96 份报告，属于有限采样，不是全量系统诊断。后续现场采集持续约 15 分钟并正常结束，但没有与用户确认复现时刻对齐的验收结果；不能写成根因已确定或修复已完成。

## 温控与电池证据的边界

当前 USB 充电时的温度不能反推历史视频通话时温度；私有电量计字段未确认契约时，不直接换算成 CPU 温度。循环次数、用户界面最大容量、日汇总容量和峰值性能提示来自不同口径，应分别标注来源和时间。

电池老化可能影响峰值供电能力，是否启用性能管理需结合系统提示和故障证据。仅凭健康百分比或循环数，不承诺换电池能解决特定挂断卡死。

## 下一次采集与修复验收

1. 保存版本、故障时刻、复现步骤与响应范围，按窗口选择必要的日志。
2. 将系统界面／触控服务、热状态、供电和内存事件按时间关联；未采到日志只表示观测不足。
3. 每次只改变有依据的一个因素，用相同任务复测，再检查是否仍有无响应及对应 watchdog。
4. 应用更新的泛化“修复已知问题”说明不证明本问题已修复；更新可作为对照项，须有复测结果。

诊断与采集通过不等于修复通过。原始日志、设备标识与配对材料留在本地证据目录，笔记只保留支撑方法的字段和案例条件。
