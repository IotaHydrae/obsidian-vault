# Linux 存储与文件系统

> 排查存储问题先确认设备类型与层次：闪存芯片、块设备、分区、文件系统、页缓存和应用数据各有不同的错误边界。

## TL;DR

- 先区分 eMMC / SD 等块设备与裸 NAND / NOR 的 MTD 路径。
- 数据写入页缓存成功不等于已经可靠持久化；核对文件系统、flush 和介质能力。
- 故障定位从内核日志、拓扑和挂载关系开始，再判断控制器、介质或文件系统层。

适用范围：Linux 6.18 LTS，硬件行为以器件规格和平台实现为准。

## 从介质到文件

```text
应用 read / write / fsync
→ VFS 与具体文件系统 → 页缓存及块 I/O
→ 块设备驱动 / MMC 等控制器 → eMMC、SD 或其他介质
```

这是常见块设备路径，不覆盖所有 I/O 模式。裸 NAND / NOR 可能走 MTD、UBI、UBIFS 等不同路径，不能把 eMMC 和裸 NAND 当成相同接口。

| 层次 | 关注什么 |
| --- | --- |
| MMC host 与 card | 控制器、供电、时钟、总线宽度、信号完整性及卡初始化 |
| eMMC / SD | 设备内部介质管理和协议；容量、分区、健康信息依产品而异 |
| 块设备与分区 | 请求和设备边界、分区表、挂载关系；设备节点名可能变化 |
| 文件系统 | 元数据、日志或检查点、空间与恢复语义，依具体文件系统而异 |
| 页缓存 / 写回 | 应用写入成功不一定已持久化；缓存策略和错误传播影响结果 |

`fsync()` 是应用请求持久化的重要接口，但整体可靠性仍取决于文件系统、块层、设备缓存、flush 支持和硬件供电。对文件创建、重命名等操作，目录元数据也可能需要单独同步；应按目标文件系统与应用协议验证断电恢复。

## eMMC、裸闪存与主机控制器

MMC 子系统负责 host、card 和请求调度等协作；host 控制器提供传输能力，eMMC 设备内部管理闪存介质。`mmcblk` 是常见块设备表示，但具体编号由发现顺序等因素决定。

裸 NAND / NOR 暴露的擦写和坏块特性与具有内部管理的 eMMC 不同，通常需要 MTD 及适合介质的上层方案。F2FS、ext4 等文件系统使用的是块设备接口；是否适合设备应结合访问模式、可靠性要求和实际测试，而不是仅按介质名称判断。

## 缓存与一致性

| 应用动作 | 能说明什么 | 还需要验证什么 |
| --- | --- | --- |
| `write()` 成功 | 数据已被内核接受相应字节数 | 是否已写回介质，后续异步错误如何反馈 |
| `fsync()` 成功 | 文件同步请求已完成到接口所能保证的层次 | 设备 flush / 缓存是否可靠，相关目录元数据是否也需同步 |
| 设备读取超时 | 对应 I/O 未按时完成 | 供电、总线、控制器、介质及驱动日志 |
| 断电后文件系统可挂载 | 元数据恢复到可用状态 | 应用事务是否完整、最新数据是否持久化 |

主机与设备端共享同一可写块设备时，不应同时以各自文件系统缓存写入；应明确所有权并完成卸载或只读隔离，避免缓存相互覆盖。

## 原子更新文件的常见步骤

对于要求断电后尽量保留一致配置的应用，可在同一文件系统内写临时文件，检查写入结果并同步文件，再执行重命名；对需要持久化目录项的场景，还要同步相关目录。跨目录重命名涉及的目录和错误处理也需考虑。

这是一种应用级更新模式，不保证所有硬件在异常断电时都符合预期。需要在目标文件系统、设备缓存和供电条件下进行断电测试，并验证同步返回值。

## 识别故障发生在哪一层

| 现象 | 下一步 |
| --- | --- |
| 设备没有出现 | 检查 host 驱动、引脚、时钟、供电、卡检测和初始化日志 |
| 块设备出现但分区缺失 | 检查分区表、容量识别和介质读取错误 |
| 文件系统挂载失败 | 核对文件系统类型、内核支持和具体错误，先保护数据 |
| 写入卡顿或掉速 | 观察写回、I/O 延迟、设备状态和内存压力，区分缓存写入与真实介质速度 |
| 重启后缺文件或内容回退 | 检查写入与同步顺序、目录项、flush 和断电条件 |

## 排查顺序

1. 从 `dmesg` 确认错误出现在控制器、介质、块 I/O 还是文件系统；同时记录设备路径和时间。
2. 用 `lsblk -f`、`findmnt` 判断设备、文件系统和实际挂载关系；不要仅凭 `/dev/mmcblkN` 的数字推断硬件身份。
3. 检查供电、时钟、总线模式、连接及温度；再按设备和文件系统的工具确认健康信息和完整性。
4. 涉及修复、格式化或写入实验前，先保护需要的数据，并确保没有其他挂载或主机同时写入。
